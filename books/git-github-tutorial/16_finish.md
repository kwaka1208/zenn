## ここまでにできるようになったこと

振り返ってみましょう。

- リポジトリを作り、変更を記録する（`init` / `add` / `commit`）
- 履歴と差分を確認する（`log` / `diff` / `show` / `blame`）
- 間違えたときに戻す（`restore` / `amend` / `reset` / `revert` / `reflog`）
- 記録しないファイルを決める（`.gitignore`）
- GitHubに公開し、取ってくる（`remote` / `push` / `clone` / `pull`）
- 並行して作業し、合流させる（`branch` / `switch` / `merge`）
- コンフリクトを解決する
- プルリクエストでレビューを受けてからマージする

これは、実際の開発現場で日常的に使われている基本操作です。ここからは、実際に使いながら慣れ、必要に応じて新しい操作を学んでいきましょう。

## いちばん大事な3つの習慣

たくさんのコマンドを紹介しましたが、身につけてほしい習慣は3つだけです。

### 1. 迷ったら `git status`

「いま何が起きているのか」がわかれば、次にすべきことは自然に決まります。Gitの操作でつまずく原因の多くは、状態を把握しないまま次のコマンドを打ってしまうことです。

### 2. こまめにコミットする

コミットしてありさえすれば、たいていの失敗は取り返せます。逆に、コミットしていない変更を守る手段はGitにはありません。「区切りがついたらコミット」を体に覚えさせてください。

### 3. pushする前に確認する

一度pushして共有されたものは、なかったことにするのが難しくなります。まずリモートの最新情報を取得し、upstreamとの差分を確認します。

```bash
git fetch origin
git status
git log --oneline "@{u}..HEAD"
git diff --stat "@{u}..HEAD"
```

`@{u}` は、現在のブランチが追跡しているupstreamブランチを表します。`git push -u origin ブランチ名` を一度実行していれば設定されています。ログでpushされるコミット、diffで変更量を確認してからpushする。それだけで、多くの事故を防げます。

:::message
初回push前などupstreamが未設定の場合、この指定は使えません。まず `git status` と `git log --oneline origin/main..HEAD` で、分岐元からのコミットを確認し、`git push -u origin ブランチ名` でupstreamを設定してください。
:::

## 練習を続けるには

### 自分のメモ帳を育てる

この本で作った `my-notes` は、そのまま使い続けられます。日々のメモをMarkdownで書いて、コミットしてpushする。それだけでも、Gitの操作は自然と身につきます。

「ブランチを切って書いて、PRを作ってマージする」という流れを、ひとりでも通してみると練習になります。

### 何かを公開してみる

GitHubに置いた静的なHTMLやMarkdownは、**GitHub Pages**でWebサイトとして公開できます。公開元には、入口となる `index.html` またはPagesで処理できる `index.md` を置いてください。

branchから公開する手順は次のとおりです。

1. リポジトリの **Settings** → **Pages** を開く
2. **Build and deployment** の **Source** で **Deploy from a branch** を選ぶ
3. 公開するbranch（たとえば `main`）を選ぶ
4. folderで `/(root)` または `/docs` を選び、**Save** をクリック
5. 公開処理が終わったら、Pages画面に表示されるURLを開く

プロジェクト用サイトは通常、`https://ユーザー名.github.io/リポジトリ名/` というURLで公開されます。公開元に指定したfolderの内容がWebへ公開されるため、秘密情報を置かないでください。

:::message alert
GitHub FreeでPagesを使えるのはPublicリポジトリです。第9章で作ったPrivateリポジトリのまま試すには、PrivateリポジトリのPagesに対応するプランが必要です。機密情報がないことを確認してPublicへ変更する、対応プランを使う、またはこの節は読むだけにする、のいずれかを選んでください。

また、Privateリポジトリから公開しても、Pagesサイトまで自動的に非公開になるわけではありません。Pagesサイトは通常インターネットへ公開されます。サイト自体のアクセス制御には、対応するEnterpriseの機能と設定が必要です。
:::

静的サイトの作り方については、次の本が参考になります。

https://zenn.dev/kwaka1208/books/astro-website-tutorial

### オープンソースに触れてみる

第14章「チームで開発する」の「フォークとオープンソースへの参加」で紹介した流れを、実際に試してみるのもおすすめです。ドキュメントの誤字修正やリンク切れの報告は、初めての貢献として取り組みやすく、それでいて確実に役立ちます。

## この本で扱わなかったこと

基本を固めることを優先したため、次のような話題は省きました。興味が出てきたら、そのとき調べれば十分です。

| 話題 | 何ができるか |
|---|---|
| `git rebase` | 履歴を並べ直して一本道にする |
| `git rebase -i` | 過去のコミットをまとめる、順番を変える、メッセージを直す |
| `git tag` | バージョン番号などの目印を付ける |
| `git worktree` | 1つのリポジトリを複数の場所に同時に展開する |
| `git bisect` | 二分探索で「どのコミットで壊れたか」を特定する |
| `git submodule` | 別のリポジトリを取り込む |
| Git LFS | 大きなファイルを扱う |
| GitHub Actions | テストやデプロイを自動化する |

このうち、次に学ぶなら **`git rebase -i`** がおすすめです。「PRを出す前に、雑に積み上げたコミットをきれいに整理する」という使い方ができ、実用性が高い機能です。

:::message
`rebase` は対象コミットを作り直すため、コミットIDが変わります。まだpushしていない自分だけのブランチなら扱いやすい一方、すでにpushして共有した履歴をrebaseすると、通常のpushでは更新できず、ほかの人の履歴とも食い違います。共有済みの履歴では原則として避け、必要な場合だけチームで合意し、作業者がいないことを確認して `--force-with-lease` などを使います。
:::

## GUIツールという選択肢

この本ではコマンドラインだけを使いました。Gitの動きを理解するには、こちらのほうが近道だと考えたからです。

一方で、日常の作業ではGUIツールが便利な場面もあります。特に、**差分を見ながら一部の行だけをステージに載せる**といった操作は、GUIのほうが圧倒的に楽です。

代表的なものを挙げておきます。

| ツール | 特徴 |
|---|---|
| VS Codeの Source Control | エディタに内蔵。追加インストール不要 |
| GitHub Desktop | GitHubとの連携が簡単。無料 |
| Sourcetree | 多機能。履歴の可視化が見やすい。無料 |
| Fork | 動作が軽快。有料（試用可） |

:::message
GUIを使うときも、この本で学んだ用語と概念はそのまま通用します。ボタンの裏で何が起きているかがわかっていれば、トラブルが起きたときにコマンドラインで対処できます。**両方使えるのがいちばん強い**、というのが実感です。
:::

## 最後に

Gitは、はじめて触るときの難しさに対して、慣れたあとの見返りがとても大きいツールです。

- 失敗を恐れずに試せる
- 「動いていたときの状態」にいつでも戻れる
- 自分がやってきたことの記録が残る
- 他の人と、混乱なく共同作業できる

これらは、ソフトウェア開発だけの話ではありません。文章を書く、設定を管理する、資料を作る。バージョン管理が役に立つ場面は、思っているよりずっと広くあります。

まずは、手元の何かひとつをGitで管理してみてください。この本が、その最初の一歩になれば幸いです。

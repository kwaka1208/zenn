## GitHub Pages以外の公開方法

前の章ではGitHub Pagesを使って公開しました。ただ、Astroが作るのは**ただのファイルの集まり**なので、置き場所はGitHub Pagesでなくてもかまいません。

次のような場合は、この章の方法が向いています。

- すでにレンタルサーバーを借りていて、そこに置きたい
- 会社や学校のサーバーに置く必要がある
- GitHubを使わずに公開したい
- 独自ドメインのサイトとして、いま使っているサーバーの一部に組み込みたい

すでにGitHub Pagesで公開できた方は、この章は読み飛ばして次の章に進んでも大丈夫です。「そういう方法もある」と覚えておいて、必要になったときに戻ってきてください。

---

## 公開するのは `dist` フォルダの中身

前の章でも一度実行しましたが、次のコマンドを実行すると、公開用のファイルが `dist` というフォルダに書き出されます。

```bash
npm run build
```

`dist` の中身はこうなっています。

```
dist/
├── 404.html
├── _astro/              # 最適化した画像・CSSなどの置き場
├── about/
│   └── index.html
├── blog/
│   ├── index.html
│   ├── first-post/
│   │   └── index.html
│   └── ...
├── tags/
│   └── ...
├── favicon.svg
├── index.html
├── rss.xml
└── sitemap-index.xml
```

中身はHTMLファイル・画像・CSSといった、**ブラウザがそのまま読めるファイル**だけです。サーバー側にPHPやデータベース、Node.jsは必要ありません。ホームページ用のスペースにファイルを置ければ、それだけでサイトが動きます。

つまり、公開作業は「`dist` の中身をサーバーにアップロードする」だけです。

:::message
`_astro` フォルダには、Astroが最適化した画像やCSSが入ります。`profile.XvvutFyz_Z6GKQC.webp` のようにファイル名へ英数字の羅列が付きますが、これは中身が変わったときだけ名前が変わる仕組みで、ブラウザに古いファイルを表示させないためのものです。気にせずそのままアップロードしてください。
:::

## 手順1：公開先のURLを設定する

`astro.config.mjs` の `site` を、実際に公開するURLに変更します。サイトマップとRSSのURLがここから作られるためです。

```js:astro.config.mjs
// @ts-check
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  site: 'https://example.com',
  integrations: [sitemap()],
});
```

サイトをドメインの直下（`https://example.com/`）ではなく、**サブフォルダ**（`https://example.com/mysite/`）に置く場合は、前章の補足で説明した `base` の設定が必要です。

```js:astro.config.mjs（サブフォルダに置く場合）
export default defineConfig({
  site: 'https://example.com',
  base: '/mysite/',
  integrations: [sitemap()],
});
```

このとき、サイト内のリンクを `url()` 経由に書き換える作業もあわせて必要になります。前章の「補足：リポジトリ名を `ユーザー名.github.io` 以外にした場合」の手順2〜4がそのまま使えるので、そちらを参照してください。

## 手順2：ビルドして手元で確認する

設定を変えたら、ビルドし直します。

```bash
npm run build
npm run preview
```

`npm run preview` は、**ビルドした結果をそのまま表示する**ためのコマンドです。開発サーバー（`npm run dev`）は書きかけのコードを表示する仕組みなので、本番と細かい違いが出ることがあります。アップロードの前にこちらで確認しておくと安心です。

ブラウザで `http://localhost:4321/` を開き、リンク・画像・ダークモード切り替えが問題なく動くことを確認してください（`base` を設定した場合は `http://localhost:4321/mysite/` です）。

## 手順3：サーバーにアップロードする

:::message alert
アップロードするのは **`dist` フォルダの中身**です。`dist` フォルダごとアップロードすると、サイトのURLが `https://example.com/dist/` になってしまいます。
:::

サーバーの公開用フォルダは、`public_html`・`www`・`htdocs` などサーバーによって名前が違います。契約しているサーバーのマニュアルで確認してください。

### FTPソフトを使う場合

FileZillaやCyberduckなどのFTPソフトでサーバーに接続し、公開用フォルダを開いて、`dist` の中身をすべてドラッグしてアップロードします。特別な設定は要りません。

:::message
タグページのフォルダ名には「カメラ」「さんぽ」のような**日本語**が入ります。FTPソフトの文字コード設定がUTF-8になっていないと、フォルダ名が文字化けしてページが開けないことがあります。タグページだけ表示できないときは、ソフトの設定で文字コード（エンコーディング）をUTF-8にしてください。
:::

### コマンドを使う場合

サーバーにSSHで接続できるなら、`rsync` というコマンドが便利です。変更があったファイルだけを転送してくれます。

```bash
rsync -av --delete dist/ ユーザー名@example.com:/path/to/public_html/
```

- `dist/` の**末尾のスラッシュ**は「フォルダの中身を送る」という意味です。これを忘れると `dist` フォルダごと送られてしまいます
- `--delete` は「サーバー側にあって手元にないファイルを削除する」オプションです。次の節で説明する「古いページが残る問題」を防げます

`--delete` は消す動作を含むので、初めて実行するときは `--dry-run` を付けて、何が起きるかだけ先に確認すると安全です。

```bash
rsync -av --delete --dry-run dist/ ユーザー名@example.com:/path/to/public_html/
```

## 更新するときの注意

### 消したはずのページが残る

FTPソフトで上書きアップロードすると、**以前アップロードしたファイルはサーバーに残ったまま**です。記事を削除したり、ファイル名（記事のURL）を変えたりすると、古いページが消えずに見えてしまいます。

対策は次のどちらかです。

- `rsync` の `--delete` を使う
- 公開用フォルダの中身をいったん削除してから、あらためて全部アップロードする

:::message alert
公開用フォルダの中身を消すときは、そのサーバーで動いている他のサイトのファイルや、サーバーの設定ファイルまで消してしまわないよう注意してください。不安なときは、消す前に丸ごとダウンロードしてバックアップを取っておきましょう。
:::

### 更新したのに変わって見えない

アップロードしたのに古い内容が表示される場合、ブラウザが以前のHTMLを覚えている（キャッシュしている）ことがほとんどです。次のキーで再読み込みしてみてください。

- Windows：`Ctrl` + `F5`
- macOS：`Cmd` + `Shift` + `R`

## 404ページを表示させる

`dist/404.html` はビルド時に作られますが、「存在しないURLが開かれたら 404.html を表示する」という判断は**サーバー側の仕事**です。GitHub Pagesはこれを自動でやってくれますが、自分のサーバーでは設定が必要な場合があります。

多くのレンタルサーバーで使われているApacheの場合は、公開用フォルダに `.htaccess` というファイルを置いて、次の1行を書きます。

```:.htaccess
ErrorDocument 404 /404.html
```

サブフォルダに置いている場合は `/mysite/404.html` のようにパスを合わせてください。nginxを使っていて設定ファイルを触れる場合は、次の指定になります。

```
error_page 404 /404.html;
```

レンタルサーバーによっては、管理画面に「エラーページ設定」の項目が用意されていることもあります。

:::message
`.htaccess` を毎回手でアップロードするのが面倒なら、プロジェクトの `public/` フォルダに置いておく方法があります。`public/` の中身はビルド時に `dist/` へそのままコピーされるので、`public/.htaccess` を作っておけば、ビルドのたびに `dist/.htaccess` が用意されます。

なお `.htaccess` のように**ドットで始まるファイルは、FTPソフトの初期設定では表示されない**ことがあります。アップロードされているか確認したいときは、ソフトの設定で隠しファイルを表示するようにしてください。
:::

## `dist` はGitに含めない

プロジェクトの `.gitignore` には、はじめから `dist/` が書かれています。ビルド結果は元のファイルからいつでも作り直せるので、Gitで保存しておく必要がないからです。

```:.gitignore（一部）
# build output
dist/
```

普段の作業はこうなります。

1. 記事を書く・コードを直す
2. `npm run dev` で確認する
3. 変更をコミットする（Gitを使っている場合）
4. `npm run build` でビルドする
5. `dist` の中身をサーバーにアップロードする

GitHub Pagesの「pushしたら自動で公開」に比べると手数は増えますが、そのぶん置き場所を自由に選べます。手元でビルドしてアップロードするだけなので、GitHubのアカウントすら必要ありません。

:::message
GitHub Pagesとこの方法は、どちらか一方しか選べないわけではありません。たとえば「普段はGitHub Pagesで公開し、同じサイトを社内サーバーにも置く」といった使い方もできます。ビルドしてできるのは同じ `dist` フォルダです。
:::

## HTTPSについて

サイトを公開するときは、`https://` で見られるようにしておきましょう。多くのレンタルサーバーでは、管理画面から無料のSSL証明書（Let's Encryptなど）を数クリックで設定できます。

`http://` のままだとブラウザに「保護されていない通信」と表示され、訪問者を不安にさせてしまいます。設定方法は契約しているサーバーのマニュアルを確認してください。

## まとめ

- Astroが作るのはただのファイルなので、**`dist` の中身をどこかのサーバーに置けば公開できます**
- 公開前に `astro.config.mjs` の `site` を実際のURLに変更します。サブフォルダに置く場合は `base` の設定も必要です
- アップロードするのは `dist` フォルダ**ごと**ではなく、その**中身**です
- 更新時は、消した記事の古いファイルがサーバーに残らないように気をつけます（`rsync --delete` が便利です）
- 404ページを表示するには、サーバー側の設定（Apacheなら `.htaccess`）が必要な場合があります
